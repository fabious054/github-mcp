# ADR 0002: Multi-account OAuth linking

## Status
Accepted (2026-09-22)

## Context

Issue #10 asks for linking any number of GitHub accounts to a single
registered connector, through successive OAuth authorizations — no manual
PAT, no duplicate connector entries.

The existing OAuth flow (`lib/oauth.ts`, `app/authorize`, `app/callback`,
`app/token`, `app/register`) is fully stateless by design: every piece of
state (registered client, authorization code, PKCE challenge) is serialized
as an encrypted blob (AES-256-GCM) that travels inside the OAuth parameters
themselves. The server never persists anything, and the "access_token" the
MCP client ends up holding is the person's real GitHub access token,
returned directly to the client — the server never sees that person again
until the next tool call, where the token simply gets forwarded to the
GitHub API.

That design gives one bearer token per connector session, by construction.
Linking N accounts to a single connector therefore requires new state to be
kept somewhere, plus a way to know which additional accounts belong to the
same person.

## Options considered

1. **Key linked accounts by the MCP `client_id`** (from Dynamic Client
   Registration, `app/register/route.ts`). Rejected: `client_id` identifies
   a *connector installation*, not a *person* — a different device/browser
   session can register a fresh `client_id`, silently losing access to
   previously linked accounts. It's also generated by an unauthenticated
   public endpoint, so it isn't a safe boundary to key account-linking data
   on.
2. **Anchor on real GitHub identity, linking only from an authenticated
   call.** The first account authorized becomes the "primary" identity
   (keyed by its GitHub login, already fetched today in
   `app/callback/route.ts` as `githubLogin`). Linking an *additional*
   account can only be initiated by a tool call that already carries a
   valid token for the primary account — proving control of the primary
   account before anything is written. Chosen.

## Decision

Anchor multi-account linking on real GitHub identity (option 2), never on a
client-generated identifier. A new `link_account` tool, callable only with a
valid primary-account token already in hand, produces a one-time
authorization URL; completing that GitHub OAuth flow appends the newly
authorized account's token to the primary identity's record.

## Storage

MongoDB Atlas, free/M0 tier (chosen by Fabio). Requires the standard
serverless connection-pooling pattern for the Vercel + Next.js + MongoDB
driver combination (cache the `MongoClient` across invocations via a module-level/global
variable, per official MongoDB/Vercel guidance — a fresh connection per
invocation would exhaust the connection limit under load). GitHub tokens
must never be stored in plaintext: reuse the existing AES-256-GCM helpers in
`lib/oauth.ts` (`encryptJson`/`decryptJson`) to encrypt each stored token,
keyed by `OAUTH_ENCRYPTION_KEY` (same secret already in use, already only on
Vercel).

## Consequences

- This is a real architecture change: the server stops being 100%
  stateless. A new secret (`MONGODB_URI`) joins
  `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET`/`OAUTH_ENCRYPTION_KEY`
  on Vercel.
- Existing single-account OAuth behavior must keep working unchanged for
  someone who never calls `link_account` (acceptance criterion #6 in issue
  #10).
- Auto-detecting which linked account to use per call (criterion #4) reads
  from this same storage; ambiguity (criterion #5) is resolved by falling
  back to the existing `account` parameter, unchanged in shape.
